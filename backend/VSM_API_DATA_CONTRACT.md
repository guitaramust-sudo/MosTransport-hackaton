# ВСМ — передача данных через API: handoff для разработки

**Статус:** проект контракта, 26.09.2026. Это описание того, какие данные нужны клиенту и внешним системам; оно не подтверждает, что маршруты уже реализованы. Фактические имена полей и маршруты сверить с разработчиками Scenario Engine и затем оформить в OpenAPI либо в актуальной API-документации репозитория.

**Источники:** [ТЗ](</Users/sergejlebedev/Downloads/Геймификация для ВСМ (1).pdf>) (с. 2–5), [QA](</Users/sergejlebedev/Downloads/video1437282599.docx>) (абз. 16–21, 77–81, 102–110), [GDD v1.0](<VSM_GAME_DESIGN_SPEC_v1.0.md>) (§§13–18, 21), [постановка Scenario Engine](</Users/sergejlebedev/Downloads/vsm_scenario_engine_task.md>) (§23). При расхождении правила рейтинга использовать GDD **v1.0**: накопленные очки, не среднее лучших попыток. Любые числа баланса в GDD — прототипные, не норматив ВСМ.

## 1. Граница данных

```text
Игрок → API Scenario Engine: команда и версия состояния
Scenario Engine → игрок: видимое состояние и последствия команды
Scenario Engine → внутренний журнал: действия, причины, effects, evidence
Finalizer → игрок: SessionResult и причинный Debrief
Progression Service → игрок: XP, компетенции, достижения, накопленные очки и рейтинг
Административный API ↔ внешняя HR/LMS: регистрация профиля и разрешённая сводка
```

Клиент **не передаёт** итоговые Safety, Loyalty, компетенции, XP или рейтинговые очки: их считает сервер. В клиентский state не включать скрытые события, будущие последствия и «правильный» приоритет. Сырой action log хранится на сервере; игрок получает объяснимый debrief после завершения. Внешней системе не отправлять сырой журнал решений без отдельного решения о целях и правах доступа.

## 2. Маршруты игрового API

`E` — маршрут уже описан в постановке Scenario Engine, **реализация не проверена**. `G` — расширение из GDD v1.0. `P` — предлагаемый read model для UI/интеграции, отсутствует в постановке движка. Наличие строки здесь не означает готовый endpoint.

| Метод и маршрут | Статус | Запрос → ответ | Обязательное правило |
|---|---|---|---|
| `GET /scenarios` | E + G | Доступный каталог → `scenario_id`, название, `scenario_version`, класс/этап, `validation_status`, оценочная длительность | Не возвращать внутреннее дерево скрытых событий. |
| `GET /scenarios/{scenario_id}` | E + G | ID → публичный briefing и метаданные | Контентная версия фиксируется при старте сессии. |
| `POST /scenario-sessions` | E + G | `scenario_id`, `wagon_class`, `mastery_stage`; `seed` только для разрешённого demo/replay → `session_id`, `state_version`, начальный видимый state | Для обычного зачётного рейса seed назначает сервер. |
| `GET /scenario-sessions/{id}` | E + G | ID → видимые активные события, `scenario_time`, текущие `metrics.safety` и `metrics.loyalty`, доступные игроку обязательства, таймеры, `state_version` | `metrics.safety` = **текущее состояние мира**, не итоговая оценка действий. |
| `POST /scenario-sessions/{id}/actions` | E + G | `event_id`, `choice_id`, `command_id`, `expected_state_version` → `state_delta`, изменившиеся видимые события, `state_version`, видимый state | Сервер применяет условия, due timers, effects и пишет причинный log атомарно. |
| `POST /scenario-sessions/{id}/tick` | E, опционально | Сигнал для продвижения времени → серверное состояние | Клиентский `elapsed` не является источником истины для дедлайна. Если clock двигается иначе, маршрут не нужен. |
| `GET /scenario-sessions/{id}/result` | E + G | ID завершённой сессии → `SessionResult` и debrief | До финализации результат не выдавать как окончательный; повтор запроса возвращает тот же результат. |

Минимальный запрос действия:

```json
{
  "event_id": "service_request_1",
  "choice_id": "verify_service",
  "command_id": "cmd_0007",
  "expected_state_version": 6
}
```

Повтор того же `command_id` возвращает прежний ответ без повторного effect. Новая команда со старой версией состояния получает `409` и актуальную `state_version`. Истечение серверного таймера нельзя отменить поздним действием клиента.

Минимальный ответ на принятое действие; внутренний журнал и будущие события сюда не включены:

```json
{
  "state_version": 7,
  "state_delta": { "metrics": { "loyalty": 3 } },
  "activated_events": [],
  "completed_events": ["service_request_1"],
  "state": {
    "scenario_time": 36,
    "metrics": { "safety": 100, "loyalty": 83 },
    "active_events": []
  }
}
```

## 3. Что возвращать после рейса

`GET .../result` должен отдавать поля в четырёх группах. Полная модель и значения полей — GDD v1.0 §21.4.

| Группа | Поля, нужные в API | Зачем клиенту |
|---|---|---|
| Идентичность результата | `session_id`, `scenario_id`, `scenario_version`, `seed`, `completed_at`, `scoring_rule_version`, `validation_status`, `points_namespace` | Показать версию, demo/approved статус и воспроизвести расчёт. |
| Итог игры | `world_safety_current`, `session_safety_score`, `loyalty`, `session_pass`, `critical_violations`, `unresolved_commitments`, `safety_incident_history` | Разделить состояние мира, качество действия и результат сессии. |
| Учебный и игровой прогресс | `competencies{score,confidence,status}`, `xp_delta`, `class_mastery_delta`, `achievements`, `leaderboard_points_delta`, `leaderboard_points_total`, `leaderboard_award_reason`, `leaderboard_eligible` | Показать освоение и начисление без смешения компетенции, XP и рейтинга. |
| Причинный разбор | `debrief[]` с `event_instance_id`, `action_id` или причиной бездействия, `effect_id`, `causal_group_id`, raw/applied влиянием на шкалы, evidence, текстом объяснения, `source_ref`, `validation_status` | Объяснить, что произошло и почему показатель изменился. |

`session_safety_score` рассчитывается из замороженного журнала и не является второй изменяемой шкалой внутри reducer. Компетенция с недостатком evidence возвращает `score:null`, `status:"insufficient"`; draft-контент не формирует официальный HR-вывод. `leaderboard_points_total` — накопленная сумма ledger; по ней строятся обязательные рейтинги бригады, депо и компании. В demo используется отдельный namespace.

Сокращённый пример **демонстрационного** результата (числа условные):

```json
{
  "session_id": "demo_session_1",
  "scenario_id": "microshift_v1",
  "scenario_version": "1.2.0",
  "seed": "S1",
  "scoring_rule_version": "points-v1",
  "validation_status": "draft",
  "points_namespace": "demo",
  "world_safety_current": 100,
  "session_safety_score": 100,
  "loyalty": 83,
  "session_pass": true,
  "competencies": {
    "communication": { "score": null, "confidence": 0, "status": "provisional" }
  },
  "leaderboard_points_delta": 0,
  "leaderboard_points_total": 0,
  "leaderboard_eligible": false,
  "debrief": [
    {
      "event_instance_id": "service_request_1",
      "action_id": "verify_service",
      "effect_id": "effect_12",
      "causal_group_id": "request_1_response",
      "metric_effects": [
        { "metric": "loyalty", "raw_delta": 3, "applied_delta": 3 }
      ],
      "evidence_ids": ["ce_1"],
      "feedback_id": "service_explanation_demo",
      "validation_status": "draft"
    }
  ]
}
```

Это пример формы ответа, не фиксация итоговой схемы: в финальный OpenAPI нужно добавить обязательные поля из GDD §21.4 и проверить ответы работающего backend. QA указывает на оценку по логу после сессии; показанные во время игры шкалы — текущие последствия, финальный результат подтверждает finalizer.

## 4. Профиль, рейтинг и внешняя интеграция

Следующие read models нужны продукту, но **не входят в исходный список маршрутов Scenario Engine**. Команда может дать им другие URL или собрать из существующего backend, сохранив состав и смысл данных.

| Предлагаемый маршрут | Статус | Минимальный ответ / ограничение |
|---|---|---|
| `GET /me/progress` | P | `xp_total`, `player_level`, освоение по классам, компетенции со `score/confidence/status`, последние результаты и достижения. Не считать `insufficient` низким навыком. |
| `GET /leaderboards?scope=brigade|depot|company` | P | `group_scope`, `group_id`, `leaderboard_points_total`, место, перцентиль, размер группы, допустимые строки. Один накопленный счёт в трёх обязательных срезах; права видимости задаёт компания. |
| `POST /admin/users` | G | Внешняя система посылает `source_system`, `external_user_id`, `assigned_class_ids`, `command_id`, необязательное `display_name`; получает внутренний `user_id` и `created|updated`. Это уточнение QA об интеграции извне, не требование LDAP. |
| `GET /admin/users/{user_id}/learning-summary` | P | Защищённая **индивидуальная** сводка для уполномоченного HR/обучения: привязка к сотруднику, результаты по классам, Safety/Loyalty, наблюдения компетенций с уверенностью и история зачтённых попыток. Состав полей — §4.1. **Только `approved`**; без автоматического кадрового решения. |

ТЗ требует документированный API для возможной интеграции с HR/LMS/биллингом, но не задаёт полезную игровую операцию для биллинга. Не придумывать транзакции оплаты или зарплатный API. Реальная авторизация, состав передаваемых персональных данных и правила кадрового применения требуют решения компании; в демо использовать только синтетические профили.

### 4.1. Индивидуальная сводка для HR и учебного контура

**Основание:** QA, абз. 11–15, связывает результаты обучения с возможным переходом между классами обслуживания; QA, абз. 77–81, просит регистрацию сотрудника извне. ТЗ, с. 2 и 5, требует аналитику компетенций и API для HR/LMS. **Точный состав HR-отчёта источники не задают**. Следующая схема — предлагаемое воплощение этих требований, не утверждённое кадровое правило.

| Блок ответа | Обязательные поля предлагаемого контракта | Как HR их читает |
|---|---|---|
| `subject` | `user_id`, `source_system`, `external_user_id`, `assigned_class_ids`; `display_name` только если разрешён политикой доступа | `source_system + external_user_id` связывает игровой профиль с записью **конкретного сотрудника** во внешней HR-системе. В демо все значения синтетические. |
| `training_scope` | `class_id`, `mastery_stage`, `class_mastery_status`, `assessed_at`, `validation_status`, `scenario_version`, `scoring_rule_version` | Какой класс и учебный этап оценивались, по каким версиям контента и правила. Учебный статус не означает допуск к работе. |
| `session_outcomes` | `approved_completed_count`, `approved_passed_count`, `recent_assessments[]` с `session_id`, датой, классом, `session_pass`, `world_safety_current`, `session_safety_score`, `loyalty`, `critical_violation_count`, незавершёнными обязательствами | Показывает, как сотрудник прошёл конкретные утверждённые рейсы. Safety поведения и восстановленное состояние ситуации видны раздельно. |
| `competencies` | Для каждого `competency_id`: `score:number|null`, `confidence`, `status`, `evidence_count`, `context_count`, ссылки на разрешённые `session_id`/эпизоды | HR видит наблюдаемый навык и силу основания. `insufficient` = данных мало, а не «сотрудник не умеет». |
| `provenance` | `as_of`, `source_ref`/версия утверждённых правил, `excluded_draft_count` или признак исключения demo/draft | Можно понять, на какой базе сделана сводка и почему часть прохождений не вошла в неё. |

Сводка собирается по `user_id`, возвращённому при `POST /admin/users`; клиент игры не может подменить `external_user_id` или рассчитанные результаты. Доступ к ней получает только роль, которой компания разрешила просмотр индивидуальных учебных результатов. При отсутствии утверждённых оценок вернуть явный статус `no_approved_data`, а не нули компетенций. При необходимости подробного разбора уполномоченный сотрудник открывает разрешённый эпизод по `session_id`; выдача полного сырого action log — отдельное решение о правах.

**Кадровая граница:** API отдаёт факты прохождения, качество решений и учебное освоение класса. Он не отдаёт `promote_to_business=true` и не делает автоматическое повышение. Условия перехода, ответственный за решение и роль игровых данных должны быть утверждены компанией. XP, уровень, достижения и место в рейтинге не подменяют Safety и компетенции при таком решении.

**Проверка контракта:** на двух синтетических сотрудниках сводки не смешиваются; draft/demo-рейс не попадает в HR-оценку; approved-рейс показывает обе Safety, Loyalty и evidence с confidence; пользователь без нужной роли получает отказ; отсутствие evidence отображается как `insufficient`, не как ноль.

## 5. Что разработчики должны подтвердить до фиксации OpenAPI

1. Какие маршруты и поля из постановки E уже реализованы; какой механизм серверного clock, таймеров и завершения реально работает.
2. Как журнал связывает решение, отложенный effect, изменение шкалы и evidence; без этих ссылок полный debrief из GDD собрать нельзя.
3. Кто реализует `SessionResult`, Progression Service и read models профиля/рейтинга: движок или отдельный backend-модуль.
4. Какие endpoints успевают работать в демо, а какие остаются документированным проектом интеграции. Это нужно обозначить в итоговой API-документации честно.
5. Как авторизуются игрок, администратор и внешняя система; доступ к индивидуальным результатам и рейтингу разделён по ролям.

**Критерий готовности API-документации для сдачи:** для каждого *реально реализованного* маршрута указаны метод, URL, request/response schema, пример, ошибки, авторизация и demo/official семантика; примеры проходят против работающего backend. Этот handoff фиксирует продуктовый состав данных и не заменяет финальный OpenAPI по коду.
