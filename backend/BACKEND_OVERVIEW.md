# Бэкенд тренажёра ВСМ: текущее состояние

Актуально для ветки `main` на 27.09.2026. Это обзор **реализованного кода**.
Точные тела запросов, ответы и HTTP-ошибки приведены в [API_CONTRACT.md](API_CONTRACT.md).
[VSM_API_DATA_CONTRACT.md](VSM_API_DATA_CONTRACT.md) описывает целевой контракт и
не должен восприниматься как список уже работающих функций.

## Что делает сервер

Go-сервис хранит игроков и ход смены в PostgreSQL, предоставляет HTTP API,
вызывает GigaChat или локальный Mock для диалога, применяет правила игры,
считает результаты и ведёт прогресс. В приложении одновременно доступны два
потока:

| Поток | Суть | Статус |
| --- | --- | --- |
| Диалоговая смена `/api/session/*` | Несколько сценариев из каталога, по одному активному; игрок пишет пассажиру и может вызвать помощь. | Работает, сохранён для совместимости с прежним экраном клиента. |
| Новая симуляция `/api/session/simulations/*` | Несколько событий одновременно, выборы и ветки, зоны вагона, обнаружение сигнала, свободный разговор, журнал причин и итог. | Работает как отдельное демо и доступна на отдельном экране клиента. |

В обоих потоках модель отвечает за речь пассажира. **Правила, состояние,
таймеры, итоговые шкалы и начисления контролирует сервер.**

## Устройство проекта

```text
cmd/server                 запуск, конфигурация зависимостей, маршруты, фоновые таймеры
cmd/bootstrap-admin        локальное назначение администратора
internal/handler           HTTP-запросы и коды ответов
internal/middleware        JWT и лимит запросов к /auth
internal/service           игровые потоки, авторизация, разбор, профиль, прогресс
internal/simulation        шаблон и детерминированный движок новой симуляции
internal/content           каталог старых сценариев и пассажиров
internal/llm               единый интерфейс GigaChat/Mock
internal/domain            структуры данных
internal/repo/postgres     хранение, транзакции и SQL-миграции
scripts/smoke_simulation.py сквозная проверка демо API
```

Запрос проходит через `handler → service → repo`; сервис вызывает `llm.LLMClient`
только там, где нужна речь или анализ текста. `internal/content/*.json` и
`internal/simulation/demo.json` встроены в бинарник через `go:embed`.
Изменение этих файлов требует новой сборки. Уже начатая новая симуляция хранит
снимок своего шаблона, поэтому обновление файла не переписывает её правила.

## Аутентификация, роли и доступ

- `POST /auth/register` создаёт только роль `user`. Пароль хешируется bcrypt.
- `POST /auth/login` выдаёт короткоживущий JWT access и случайный refresh-токен.
  В базе хранится SHA-256 refresh-токена; обновление через `/auth/refresh`
  одноразовое и выдаёт новую пару.
- Все `/api/*` требуют `Authorization: Bearer …`. Доступ к чужим сменам и
  ситуациям проверяется по `player_id`. `/admin/*` требует роль `admin`.
- Администратор создаётся или повышается локальной командой
  `cmd/bootstrap-admin` с `ADMIN_BOOTSTRAP_EMAIL` и `ADMIN_BOOTSTRAP_PASSWORD`.
  Для повышения существующего аккаунта нужен его пароль. Публичная
  регистрация по адресу администратора не даёт эту роль.
- `/auth/*` ограничен десятью запросами в минуту на адрес подключения.
  В `APP_ENV=production` обязателен собственный `JWT_SECRET` и запрещён
  `GIGACHAT_INSECURE`.

Административное API также умеет создавать/обновлять внешнего пользователя по
`source_system + external_user_id`, отдавать сводку обучения и утверждать
завершённую **диалоговую** смену. Сводка учитывает только утверждённые
результаты. Утвердить смену с `draft`-сценарием нельзя.

## Поток 1: диалоговая смена

1. `POST /api/session/start` выбирает из каталога несколько сценариев
   (`SITUATIONS_PER_SESSION`, по умолчанию 4) и случайных пассажиров.
   Сначала активна одна ситуация; следующие лежат в очереди и открываются
   после закрытия предыдущей.
2. `POST /api/situation/{id}/message` сохраняет реплику игрока и ответ
   пассажира. В `gigachat` ответ приходит от GigaChat, в `mock` — от локального
   имитатора. История хранится в `messages`, так что разговор переживает
   перезапуск сервера. При ошибке модели игрок получает резервную реплику.
3. `POST /api/situation/{id}/escalate` фиксирует вызов адресата: начальника
   поезда, ПТБ, полиции, медика или скорой. Обязательность и допустимые
   адресаты заданы сценарием.
4. Закрытие ситуации — явное, по завершении смены или по истечении её срока.
   Модель возвращает наблюдения о диалоге (переданные пункты, тон), после чего
   код по таблице замечаний вычисляет `success`, `partial`, `fail` или
   `timeout`, XP, лояльность и безопасность. Шкалы этого потока обновляются
   при закрытии ситуации, а не после каждой реплики.
5. `POST /api/session/{id}/finish` закрывает оставшееся, возвращает разбор
   всей смены и один раз начисляет XP и evidence компетенций. Повторный вызов
   не удваивает начисление. Диалоговые смены пока **не дают очков рейтинга**.

Каталог содержит 50 сценариев и 50 пассажиров. Все 50 сценариев сейчас имеют
`validation_status=draft`. При `POINTS_NAMESPACE=demo` они доступны для игры;
при `official` доступны только `approved`, которых в текущей поставке нет.
Медицинские и критические кейсы из каталога остаются демонстрационными
гипотезами, а не утверждёнными рабочими процедурами.

## Поток 2: новая симуляция

Шаблон `demo_service_branch` версии `1.1.0` хранится в
`internal/simulation/demo.json`. Он содержит шесть узлов событий. В начале
активны обращение за услугой, спор о месте и скрытый мокрый пол; первые два
видны сразу, сигнал о третьем находится в багажной зоне.

При `POST /api/session/simulations` сервер случайно выбирает имя пассажира,
темперамент, запрос на бытовую услугу и напряжение от 1 до 3. GigaChat или
Mock формирует вступительную реплику. Эти параметры закрепляются за сменой.
Варианты `A/B` сейчас меняют порядок первых двух событий; это **не два
независимых сценария**.

Игрок может:

- выполнять готовый выбор через `POST …/{id}/actions`;
- написать пассажиру свободный текст через `POST …/{id}/dialogue`;
- перейти между салоном и багажной зоной (`move_to`) и осмотреть сигнал
  (`inspect`).

Для свободного текста модель возвращает короткую реплику пассажира и
предлагает `choice_id`, только если распознала явное действие. Сервер принимает
ID лишь из доступных сейчас вариантов, проверяет необходимые флаги, зону и
версию состояния. Если решения нет или ответ модели некорректен, разговор
продолжается без перехода. Длина реплики игрока ограничена 600 символами,
в смене допускается до 12 диалоговых ходов. История разговора и решения
сохраняются в состоянии смены.

Серверное игровое время увеличивается на 3 секунды за уточнение, 5 за осмотр,
6 за выбор и 8 за переход между двумя зонами. Демонстрационный дедлайн услуги
равен 300 секундам и начинается после генерации вступления. Фоновый цикл
проверяет сроки примерно каждые 2 секунды; истечение переводит обращение в
ветку пропущенного окна один раз. Запрос клиента тоже проверяет срок.

Каждая команда несёт UUID `command_id` и `expected_state_version`.
PostgreSQL блокирует строку смены, применяет действие и записывает результат
в одной транзакции. Повтор того же ID возвращает сохранённый результат,
устаревшая версия получает `409`. Это защищает от двойного применения выбора
при повторной отправке или параллельных запросах.

После закрытия всех событий `GET …/{id}/result` отдаёт журнал действий,
изменения шкал, объяснение и более удачные доступные варианты. Для решений
через диалог в разборе видны текст игрока и ответ пассажира. Хеш результата
включает журнал и диалог. Смена зачтена, когда нет timeout,
`session_safety_score ≥ 90`, текущая безопасность `≥ 90` и лояльность `≥ 60`.
Это **демо-правила**, а не профессиональная аттестация.

## Прогресс, достижения и рейтинг

- `GET /api/profile` возвращает игрока, уровень по XP, предварительные
  показатели компетенций, достижения и отдельную сумму очков рейтинга.
- `first_complete` выдаётся за первую зачтённую новую симуляцию;
  `first_signal` — за первое обнаружение скрытого сигнала.
- Недельный UTC-челлендж требует зачесть варианты `A` и `B`; награда `+5 XP`
  выдаётся один раз за неделю. Прогресс есть в `/api/challenges/weekly`.
- `/api/notifications` отдаёт сохранённые уведомления о новом демо-сценарии,
  старте и завершении челленджа. Это получение через API, не push-доставка.
- Очки рейтинга находятся в `points_ledger`, отдельно от `players.total_xp`.
  Зачтённая новая симуляция даёт 20 очков за первый вариант семейства и 10
  за второй; повтор того же варианта, провал и timeout дают 0. Это временный
  баланс. `demo` и `official` изолированы, а официальный реестр принимает
  только `approved` контент. XP челленджа в рейтинг не входит.
- `/api/leaderboard` отдаёт топ-10, `/api/leaderboards` — топ-50 по компании,
  депо или бригаде. Место, полный размер группы и перцентиль рассчитываются
  до ограничения списка; игроки с равными очками делят место.

## Хранение и фоновые операции

PostgreSQL содержит `players`, `sessions`, `situations`, `messages`,
`player_competencies`, `refresh_tokens`, `simulation_runs`,
`simulation_commands`, `achievements`, `challenge_awards`, `notifications` и
`points_ledger`. Состояние новой симуляции и снимок шаблона лежат в JSONB;
команды и начисления имеют уникальные ключи для идемпотентности.

Миграции `001`–`008` встроены в бинарник и применяются при старте под
транзакционной advisory-блокировкой. Пул PostgreSQL ограничен десятью
соединениями, SQL-запрос — 30 секундами. В фоне сервер закрывает просроченные
диалоговые ситуации и продвигает таймеры новых симуляций.

## Запуск и проверка

Из каталога `backend/`:

```bash
docker compose up --build
curl http://localhost:8088/readyz
python3 scripts/smoke_simulation.py
```

По умолчанию работает `LLM_MODE=mock`, ключи не нужны. Для GigaChat задать
`LLM_MODE=gigachat`, `GIGACHAT_CLIENT_ID` и `GIGACHAT_CLIENT_SECRET` через
окружение (не коммитить секреты). Остальные параметры описаны в [README.md](README.md).

Проверки Go из каталога `backend/`:

```bash
go build ./...
go vet ./...
TEST_DATABASE_URL='postgres://vsm:vsm@localhost:5432/vsm?sslmode=disable' go test ./... -count=1
TEST_DATABASE_URL='postgres://vsm:vsm@localhost:5432/vsm?sslmode=disable' go test -race ./internal/service ./internal/repo/postgres -count=1
```

Сквозной скрипт создаёт две тестовые учётные записи и проверяет ветвление,
свободный диалог, повтор команды, чужой доступ, разбор, достижения, челлендж,
уведомления и рейтинг. Тесты с `TEST_DATABASE_URL` требуют работающий
PostgreSQL; без переменной интеграционные тесты пропускаются.

## Границы текущей реализации

1. В новой симуляции один граф событий. Рандомизация меняет пассажира,
   бытовой запрос, напряжение и порядок событий; GigaChat формирует речь и
   предлагает разрешённые ветки. Он **не генерирует новые проверенные
   процедуры или механики**.
2. Все поставляемые сценарии и новый шаблон имеют статус `draft`. Требуются
   экспертная проверка содержания, утверждённые источники и баланс очков,
   прежде чем использовать систему для профессиональной оценки.
3. Компетенции в профиле пока имеют статус `insufficient` или `provisional`;
   финальное подтверждение освоения не реализовано. Диалоговая смена всё ещё
   считает шкалы при закрытии ситуации, в отличие от новой симуляции.
4. `LLM_MODE=mock` проверен автоматическими и сквозными тестами. Интеграция с
   реальным GigaChat требует действующих ключей и отдельной проверки качества
   ответов и распознавания намерений.
5. Уведомления доступны по запросу к API; отдельной push-инфраструктуры нет.
