# Real-time вагон: контракт и поведение

Новый режим использует существующие диалоговые ситуации и отдельный серверный
цикл для появления событий и перемещения по вагону. Сейчас доступен только
класс `standard`; `comfort`, `business` и `first` возвращаются как
`coming_soon`. Это демонстрационный контент со статусом `draft`.

## Запуск

Все HTTP-запросы ниже, кроме WebSocket handshake, требуют
`Authorization: Bearer <access_token>`.

`GET /api/wagon/classes` возвращает `200`:

```json
{"classes":{"standard":"available","comfort":"coming_soon","business":"coming_soon","first":"coming_soon"}}
```

`GET /api/wagon/levels` возвращает уровни конкретного игрока по порядку:

```json
{"levels":[{"id":"orientation","order":1,"title":"Ориентация в вагоне","intro":"Первая смена...","status":"unlocked"},{"id":"service_basics","order":2,"title":"Сервисные просьбы","status":"locked"}]}
```

`status` принимает `locked`, `unlocked` или `passed`. Для закрытых уровней
`intro` отсутствует. Уже пройденный уровень можно запустить повторно.

`POST /api/session/wagon/start` с телом `{"level_id":"orientation"}` возвращает
`201`:

```json
{"session_id":"<uuid>","ws_path":"/api/wagon/<uuid>/ws"}
```

Неизвестный уровень даёт `404`, закрытый — `409` и `{"status":"locked"}`.
Если класс уровня недоступен, сервер возвращает `409` и
`{"status":"coming_soon"}`. При `POINTS_NAMESPACE=official` без
утверждённых сценариев запуск даёт `409`.

## WebSocket

Подключение: `GET /api/wagon/{session_id}/ws?token=<access_token>` через
WebSocket. Токен проверяется как обычный JWT, включая актуальную роль в БД;
подключиться может только владелец активной смены. Допустимые браузерные
`Origin` задаются `CORS_ORIGINS`. При новом подключении старое соединение
заменяется, а сервер сразу отправляет полный снимок состояния.

Форма сообщения сервера:

```json
{
  "type":"state",
  "game_time_s":12,
  "wagon_state":{
    "class_id":"standard",
    "level_id":"orientation",
    "restricted_anchors":["staff_zone"],
    "player":{"at":"service_point"},
    "carried_items":[],
    "started_at":"2026-09-27T12:00:00Z",
    "duration_s":480,
    "seats":[
      {"anchor":"seat_1","passenger_def_id":"<id>","actor":{"at":"seat_1"},"situation_id":"<uuid>","situation_def_id":"cold"}
    ]
  },
  "active_situations":[{"situation_id":"<uuid>","seat_anchor":"seat_1","type":"cold","pool":"easy"}]
}
```

`seats` на деле содержит шесть мест. Пока ситуация не появилась, у места нет
`situation_id`. Текст ситуации не рассылается: клиент отображает пассажира и
его анимацию по `type`. Когда игрок обращается к пассажиру, клиент получает
детали через `GET /api/situation/{id}` и ведёт разговор по обычным REST
маршрутам. `actor.moving` и `player.moving` содержат `from`, `to`,
`started_at`, `duration_s`; это символьные якоря для анимации на фронтенде,
координат в ответе нет. У места может появиться `restricted_reached: true`.

Клиент отправляет одну из команд:

```json
{"type":"move_to","anchor":"seat_1"}
{"type":"pick_item","item":"blanket"}
{"type":"give_item","item":"blanket","situation_id":"<uuid>"}
{"type":"redirect","situation_id":"<uuid>"}
```

Успех подтверждается следующим `state`, ошибка —
`{"type":"error","message":"..."}`. Сервер сам хранит позицию игрока:
`move_to` занимает 3 секунды, во время движения другие позиционные действия
отклоняются. `pick_item` возможен у `service_point`, `give_item` и `redirect`
требуют находиться у пассажира с активной ситуацией. Для `give_item` нужен
предмет из инвентаря, совпадающий с сохранённым физическим требованием.
Выдача или перенаправление атомарно меняет состояние вагона и выставляет
`physical_action_done`; ситуация остаётся активной до REST-закрытия.

## Диалог, время и завершение

`GET /api/situation/{id}`, `POST .../message`, `POST .../escalate` и
`POST .../finish` работают для вагонной ситуации по прежнему контракту.
GigaChat или Mock отвечает пассажиром и оценивает диалог; факт физического
действия подтверждает сервер. Слова о якобы доставленном предмете без команды
`give_item` не засчитываются.

Каждую секунду сервер обновляет движение и отправляет снимок; раз в 3 секунды
проверяет возможность новой ситуации. Одновременно активны не более трёх
ситуаций. Типы сценариев выбираются по весам активного уровня из
`internal/content/levels.json`; `pool` в снимке остаётся меткой сложности, но
не ограничивает время появления. После 480 секунд новые ситуации не появляются. Таймеры
отдельных ситуаций закрывает прежний фоновый обработчик. Если пассажир достиг
`staff_zone`, нарушение сохраняется и снижает оценку, даже если затем игрок
его вернул.

`POST /api/session/{id}/finish` закрывает оставшиеся ситуации, возвращает
разбор смены и останавливает цикл вагона. `GET /api/session/{id}` позволяет
восстановить состояние после переподключения. При перезапуске сервера активные
вагонные смены поднимаются из PostgreSQL. Вагонный режим начисляет XP по
старому диалоговому скорингу; очки нового `points_ledger` он не начисляет.
После завершения уровень засчитывается, если в смене нет ситуации с итогом
`fail`; следующий уровень открывается последовательно.

В каталоге 54 сценария и 50 пассажиров. Четыре физических сценария — `cold`,
`thirsty`, `tired`, `zone_intrusion`. В старом последовательном режиме они не
выбираются, поскольку там нет команд перемещения и предметов.
