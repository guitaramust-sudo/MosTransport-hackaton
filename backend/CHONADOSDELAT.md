# ВСМ — что делаем в ближайшей сборке

**Статус:** объём ближайшей сборки, 27.09.2026. Команда продукта в этой беседе подтвердила первую главу `B01–B02`, призовые очки и push на Android как обязательные. Остальная последовательность — моя рекомендация для сокращения объёма. Это приоритеты реализации, а не замена [полного GDD](<VSM_GAME_DESIGN_SPEC_v2.0.md>). «Сейчас» означает следующую демонстрируемую хакатонную сборку. Текущий снимок кода — локальный `MosTransport-hackaton/origin/main@4472a2d`; удалённую ветку перед началом работы нужно сверить, потому что локальный fetch не прошёл. `draft/demo` не становится утверждённой инструкцией проводника или официальной оценкой HR.

## Что уже есть и переиспользуем

- В backend есть авторизация, профиль/XP, два достижения, накопительный рейтинг, недельный челлендж и внутренние уведомления. Есть **отдельные** ветвящаяся симуляция и real-time вагон; текущий playable вагон — Standard. Это не готовый единый учебный поток First.
- Берём существующий Scenario Engine, журнал действий, таймер, расчёт результата и ledger очков. Новый движок сюжета, новая формула рейтинга и переписывание уже работающих потоков в объём ближайшей сборки не входят.

## P0 — обязательно для ближайшего демо

| Блок | Делаем сейчас | Проверка готовности |
|---|---|---|
| **Один вагон First** | Подключить имеющуюся 3D-модель к серверному классу `first` и именованным точкам: места пассажиров, туалет, сервисная точка, граница кабины, вода и точка огнетушителя. Шесть моделей пассажиров — предел; активно сначала 1–2. Класс назначен сервером демо-аккаунту, игрок его не выбирает. | Игрок входит именно в First; может осмотреть точки B01; закрытая зона и огнетушитель не предлагают неутверждённых действий. Если First не готов, можно показать технический fallback Standard с честной маркировкой, но P0 остаётся незавершённым. |
| **Первая глава `B01–B02`** | Карта с шестью названиями глав и двумя кругами первой главы. `B01`: теория → тест из двух вопросов → 3D-ориентирование → второй тест → разбор. После его завершения открывается `B02`: теория → тест → один NPC с косвенным сигналом → подход, диалог и уточнение просьбы → второй тест → разбор. У каждого урока свой постоянный бейдж и `+20` lesson XP только за первый успех. Остальные круги видны закрытыми с причиной. | Нельзя начать практику без теории; `B02` закрыт до завершения `B01`; повтор/двойной API-вызов не дублирует XP и бейдж; оба разбора доступны повторно. Тексты и ID берутся из GDD §29. |
| **Одна содержательная смена First** | На том же вагоне запустить **одну фиксированную demo-сборку** из существующих шаблонов: пассажир A просит доступный плед; после обещания пассажир B поворачивает голову и лишь в диалоге спрашивает, где туалет. Игрок выбирает порядок, помнит обещание A и возвращается. У невыполненного обещания — одно отложенное последствие и **одна работающая demo-ветка с серверным таймером** (это игровой срок, не норма сервиса). До диалога причина сигнала B скрыта; через 7–8 секунд появляется нейтральный `!`. | Два события действительно сосуществуют; выбор меняет состояние и следующий исход; timer меняет состояние по timeout; журнал и разбор объясняют причину. Невозможный путь/предмет не создаётся. |
| **Результат и мотивация** | Показать исход смены, Safety, Loyalty, причинный debrief, уже существующие достижения/XP и **накопленные** очки рейтинга в отдельном demo namespace. На сервере сохранить действующее правило очков `20/10/0` для ветвящейся симуляции; B01 и B02 дают отдельный одноразовый lesson XP, без двойного начисления. | Повтор финализации не меняет счёт; рейтинг суммирует очки, не усредняет попытки; demo-результат не попадает в официальный HR score. |
| **Призовые очки** | Отдельный `PrizeCreditLedger`: `+10` за первое успешное завершение каждого из B01/B02, `0` за повтор. Каждая запись истекает через `6×24 h` по серверному UTC. В профиле — действующий баланс, дата ближайшего истечения и моковый прогресс к футболке `50` очков; без заказа/выдачи приза. | После двух уроков обычный demo-аккаунт имеет `20/50`; повтор не прибавляет. По истечении одной записи уменьшается только призовой баланс: XP, бейджи и накопленный рейтинг не меняются. |
| **Push при закрытом приложении** | Для Android-телефона два серверных повода: `lesson_unlocked` после B01 с переходом в B02 и `prize_credit_expiring` за 24 часа до истечения каждой активной призовой записи с переходом в собственный прогресс. Получить разрешение, сохранить device token, отправить один раз на `(user,event_type,source_id)`. Текст не раскрывает скрытую ситуацию. | На Android-телефоне push приходит при закрытом приложении и открывает нужный экран. Если разрешение отклонено, результат/награды не меняются; внутреннее уведомление допустимо как запасной канал, но не подменяет проверку push. |
| **Минимальный API между командами** | Согласовать поля карты/B01–B02, ответов двух тестов в каждом уроке, старта практики, неизменяемого результата, бейджей, `prize_balance/entries/expires_at` и регистрации Android push token. Действия вагона и сценария по возможности идут через действующие маршруты; новые URL утверждаются после сверки с роутером. | Фронт может пройти путь «логин → B01 → B02 → смена → разбор → профиль/рейтинг» без ручной подмены данных. Ключи правильных ответов и скрытый тип ситуации не приходят клиенту заранее. |

Для проверки шестидневного срока и порога `50` не ждём реальные шесть дней: отдельный синтетический demo-аккаунт получает тестовую призовую запись `+40` с `awarded_at=now−5d` и `expires_at=now+24h`, то есть с тем же правилом `6×24 h`. Первый урок добавляет ещё `+10` и показывает `50/50`; push об истечении отправляется по этой записи. Обычный новый аккаунт после B01–B02 показывает `20/50`. Тестовая запись помечена `demo_seed` и не является наградой реального сотрудника.

**Порядок backend-задач:** (1) согласовать один адаптер 3D↔Scenario Engine и конфиг First; (2) провести B01–B02 через состояние урока, тесты и неизменяемый результат; (3) подключить смену, одноразовый XP/бейдж и накопительный demo ledger; (4) добавить отдельный prize ledger; (5) отправлять два типа push из сохранённых доменных событий. Каждый пункт принимается отдельно; P0 нельзя объявить готовым по одним моковым экранам.

**Вертикальный срез важнее количества контента:** B01–B02 показывают обучение от ориентирования до первого разговора, а отдельная смена — нелинейность, одновременные задачи, последствия и рейтинг из ТЗ. Для P0 не требуется сделать все 21 урок playable. Шесть глав и тексты остальных уроков остаются в GDD как контентный план.

## Следом, только после P0

**P1, если остаётся время:** `B03` как следующий полный круг; затем Standard как второй корректно сконфигурированный вагон. Приоритет внутри P1 — сначала новый урок на том же First, потом второй класс: это не размножает одновременно контент и интеграцию.

**Не включать в задачу бэкенда сейчас:** все 21 урок и четыре playable класса; бесконечную смену (§32 GDD); чужие профили; числовую кадровую готовность/автоперевод; официальный HR-экспорт; голос, CMS, реальные призы. Обычная сумка, сценарий доступности и применение оборудования требуют отдельных проверенных процедур; не превращать их в оцениваемые рабочие инструкции ради демо. Уже работающие профиль, рейтинг, достижения и уведомления не удалять.

## Кто что должен решить до начала

1. **3D/фронт:** передать `anchor_id → asset_id/transform` для First и подтвердить, что нужные модели/анимация головы доступны в сборке.
2. **Backend и фронт вместе:** выбрать существующий endpoint/адаптер для связи 3D-вагона со Scenario Engine; зафиксировать поля запроса/ответа до параллельной реализации.
3. **Мобильная команда:** подготовить Android-телефон и development build с push. В текущем Expo-клиенте нет `expo-notifications`; нужны пакет, разрешение устройства, токен и Android FCM credentials. Push в Expo Go не считается проверкой: по [документации Expo](https://docs.expo.dev/push-notifications/push-notifications-setup/) нужна собственная сборка. Секретные ключи не класть в репозиторий.
4. **Владелец содержания:** оставить demo-флаги услуг и тексты `draft`, пока не проверены реальные правила; в демо использовать синтетические аккаунты.

**Готово, когда** один синтетический пользователь проходит указанный путь на Android-телефоне, серверный лог воспроизводит результаты обоих уроков и смены, повтор запросов не дублирует награды, призовой баланс/истечение отделены от XP и рейтинга, push приходит при закрытом приложении, а отсутствие B03–G02 и бесконечного режима не блокирует демо. Всё сверх этого — отдельная задача с собственной оценкой.
